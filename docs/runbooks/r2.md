# Cloudflare R2 cutover runbook

BeLib keeps local storage for development/E2E and uses the same backend authorization boundary for R2. Do not commit R2 credentials.

## Required runtime values

```text
BOOK_FILE_STORAGE_DRIVER=r2
R2_ACCOUNT_ID=<Cloudflare account id>
R2_ACCESS_KEY_ID=<R2 S3 access key id>
R2_SECRET_ACCESS_KEY=<R2 S3 secret access key>
R2_BUCKET_NAME=<private bucket name>
R2_ENDPOINT=                         # optional; derived from account id when blank
```

The runtime token should be limited to the BeLib bucket with object read/write permissions. A broader Cloudflare admin token is not required by the application.

## Bucket policy

Keep the bucket private. BeLib uploads through the backend and issues a presigned GET URL only after Better Auth and `RoleBookPermission` checks.

Browser requests to a presigned URL are cross-origin, so configure R2 CORS for the deployed frontend origin. Example for a production origin:

```json
[
  {
    "AllowedOrigins": ["https://belib.example.com"],
    "AllowedMethods": ["GET", "HEAD"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag", "Content-Length", "Content-Type", "Cache-Control", "Content-Disposition"],
    "MaxAgeSeconds": 3600
  }
]
```

Replace the example origin with the real BeLib frontend origin. Do not use `*` for `AllowedOrigins` in production.

## Read-only bucket preflight

The former `backend/scripts/verify-r2.ts` credential smoke writes a temporary
object, requests signed GET access, downloads object content, and deletes the
object. Do not run `npm run verify:r2` against a protected or production R2
bucket. That utility is not a read-only check.

For an explicitly opted-in bucket-access check, use the root-level script from
the repository root after backend dependencies are installed. Supply the
existing R2 account, bucket, and credentials through the process environment
without echoing them, and set `BELIB_R2_READ_ONLY_PREFLIGHT=1`:

```bash
node scripts/verify-r2-readonly.mjs
```

The script derives the Cloudflare endpoint from `R2_ACCOUNT_ID`; it rejects a
non-empty `R2_ENDPOINT` override and accepts no command-line arguments. It
uses only the S3 `HeadBucket` operation for `R2_BUCKET_NAME`. It does not
access an object, create a fixture, or print the bucket name, account ID,
endpoint, credentials, or request details. The command succeeds only when the
named bucket check succeeds. This proves bucket-level access for that credential at
that time; it does **not** prove that any object exists, that object bytes are
intact, that BeLib authorization works, or that browser CORS is configured.
An offline fake-client test is available as
`node --test scripts/verify-r2-readonly.test.mjs` and makes no network calls.

### Optional known-object metadata preflight

The script also supports a separate explicit opt-in for a previously known
BeLib object key. It requires both `BELIB_R2_READ_ONLY_PREFLIGHT=1` and
`BELIB_R2_OBJECT_READ_ONLY_PREFLIGHT=1`, plus
`R2_PREFLIGHT_OBJECT_KEY=books/<uuid>.(pdf|epub)`. It sends one S3
`HeadObject` request and checks only object metadata; it does not download the
object or verify its bytes. Leave the object opt-in unset to retain the
bucket-only behavior. Optional `R2_PREFLIGHT_EXPECTED_CONTENT_LENGTH` and
`R2_PREFLIGHT_EXPECTED_ETAG` values add exact metadata comparisons and cause
failure when a supplied value is missing or differs. ETag is an opaque object
metadata value here, not a cryptographic checksum. The key and all configuration
details are suppressed from console output.

No known pre-existing object key was available for this offline recovery
follow-up, and no live R2 request was made. A successful fake-client test only
verifies the command wiring and comparisons; it does not establish that an R2
object exists or that its contents are intact.

## Cutover checks

1. The read-only bucket preflight is green in the approved runtime context; do
   not use the legacy mutating `npm run verify:r2` command for this gate.
2. R2 bucket CORS allows the exact production frontend origin.
3. The production environment has `BOOK_FILE_STORAGE_DRIVER=r2` and all required R2 values.
4. Deploy the release candidate and register a non-sensitive test PDF/EPUB through the Admin UI.
5. Confirm the object exists below `books/` in R2 and the DB `BookFile.fileUrl` matches the strict `books/<uuid>.(pdf|epub)` object-key format.
6. Open the book as an authorized user and confirm `/api/v1/books/:bookId/file` returns signed URL metadata, then the browser fetches that URL without session credentials and receives the file.
7. Confirm an unauthorized user cannot obtain new signed URL metadata from the BeLib endpoint.
8. Delete the test data through an approved application lifecycle path when that lifecycle is implemented; do not manually delete production book objects while DB rows still reference them.

## Existing local data

Do not switch a database containing local-storage `BookFile.fileUrl` rows directly to the R2 driver. Local rows contain local keys such as `<uuid>.pdf`, while new R2 rows use `books/<uuid>.pdf`.

If existing data must be carried into R2, use a dedicated migration that uploads each local file, verifies size/hash, updates the corresponding DB row only after the R2 object is verified, and records rollback evidence. That migration is not part of the initial empty-production cutover.

## Current remaining requirement gap

The R2 URL is valid for one hour, but the current readers fetch the protected file into a Blob at open time. Reader-side automatic URL reissue before expiry is therefore not yet implemented as a long-lived direct-URL workflow. Do not mark Phase D complete until that requirement is either implemented or explicitly revised.
